# 元数据知识库构建：表 + 字段同步全流程

> 本文只讲一条链路：**把 meta_config.yaml 里的表、字段配置，补齐真实类型和示例值后，写进 MySQL meta 库**。
> 目的：彻底搞懂"分层架构 + 数据是怎么一步步流动的"。

---

## 一、一句话总览

> **配置描述先变成业务实体，业务实体再补齐真实结构与样本，最后以事务方式落到元数据库。**

展开说就是三件事：

1. **读配置**：yaml 里写了"有哪些表、每个表有哪些字段、字段的别名和含义"。
2. **补真实信息**：yaml 没写"字段的真实 SQL 类型是什么、真实值长什么样"，这些得去 dw 库查。
3. **落库**：把两者合并后的完整信息，写进 meta 库（一个"关于数据的元数据"仓库）。

---

## 二、分层架构（先建立整体地图）

项目分了 7 层，每层只管一件事。**记住一句话：上层只描述"要什么"，下层负责"怎么干"。**

```
┌─────────────────────────────────────────────────────────────┐
│ scripts/       入口层  解析命令行 -c 参数，启动异步流程          │
│                    ↓  调 service.build()                      │
│ services/      编排层  决定"先做什么再做什么"（业务顺序）         │
│                    ↓  调 repository 的方法                     │
│ repositories/  仓储层  决定"数据从哪来、写到哪去"（数据读写）      │
│                    ↓  调 mapper / 直接执行 SQL                 │
│ mappers/       转换层  业务实体 ⇄ ORM 模型 互转                  │
│                    ↓                                          │
│ entities/      实体层  纯数据载体（TableInfo / ColumnInfo）      │
│ models/        模型层  ORM 定义（对应 meta 库的表结构）           │
│                    ↓                                          │
│ clients/       连接层  外部服务连接（MySQL/Qdrant/ES/Ollama）    │
└─────────────────────────────────────────────────────────────┘
```

**本链路涉及的文件（按调用顺序）：**

| 顺序 | 文件 | 层 | 职责 |
|---|---|---|---|
| 1 | `scripts/build_meta_knowledge.py` | 入口 | 解析 `-c` 参数，创建 Session、Repository、Service |
| 2 | `services/meta_knowledge_service.py` | 编排 | `build()` → `_save_tables_to_meta_db()` |
| 3 | `repositories/mysql/dw/dw_mysql_repository.py` | 仓储 | 查 dw 库真实类型、示例值 |
| 4 | `repositories/mysql/meta/meta_mysql_repository.py` | 仓储 | 把实体写进 meta 库 |
| 5 | `repositories/mysql/meta/mappers/table_info_mapper.py` | 转换 | TableInfo ⇄ TableInfoMySQL |
| 6 | `repositories/mysql/meta/mappers/column_info_mapper.py` | 转换 | ColumnInfo ⇄ ColumnInfoMySQL |
| 7 | `entities/table_info.py` | 实体 | 表元数据载体 |
| 8 | `entities/column_info.py` | 实体 | 字段元数据载体 |
| 9 | `models/table_info.py` | 模型 | `table_info` 表 ORM |
| 10 | `models/column_info.py` | 模型 | `column_info` 表 ORM |
| 11 | `models/base.py` | 模型 | ORM 基类 |

## 三、完整执行顺序（10 步，对号入座）

对照你总结的流程，每步落在哪一层、哪段代码：

```
① 脚本读取 meta_config.yaml
   └─ build_meta_knowledge.py: await service.build(Path(args.conf))

② MetaKnowledgeService.build(config_path) 进入表链路
   └─ services/meta_knowledge_service.py: build() → if meta_config.tables:

③ 遍历配置中的每张表，构造 TableInfo
   └─ _save_tables_to_meta_db(): for table in meta_config.tables:
        table_info = TableInfo(id=table.name, name=..., role=..., description=...)

④ 通过 DWMySQLRepository.get_column_types(...) 查询真实类型
   └─ column_types = await self.dw_mysql_repository.get_column_types(table.name)

⑤ 遍历字段，通过 get_column_values(...) 查询示例值
   └─ for column in table.columns:
        column_values = await self.dw_mysql_repository.get_column_values(table.name, column.name, 10)

⑥ 构造 ColumnInfo
   └─ column_info = ColumnInfo(id=f"{table.name}.{column.name}", type=column_types[column.name], ...)

⑦ 打开一笔事务
   └─ async with self.meta_mysql_repository.session.begin():

⑧ MetaMySQLRepository 接收实体，Mapper 转 ORM 模型
   └─ save_table_infos() / save_column_infos() → TableInfoMapper.to_model(...) / ColumnInfoMapper.to_model(...)

⑨ session.add_all() 把 ORM 对象加入 Session
   └─ self.session.add_all([...])

⑩ 事务结束统一提交，数据真正写入 Meta MySQL
   └─ async with begin() 块退出时自动 commit
```

## 四、逐层代码走读（关键代码 + 为什么）

### 4.1 入口：`build_meta_knowledge.py`

```python
async with (
    meta_mysql_client_manager.session_factory() as meta_session,
    dw_mysql_client_manager.session_factory() as dw_session,
):
    meta_repo = MetaMySQLRepository(meta_session)   # 写 meta 库
    dw_repo = DWMySQLRepository(dw_session)          # 读 dw 库
    service = MetaKnowledgeService(meta_repo, dw_repo)
    await service.build(config_path)
```

**关键点：依赖注入。** Service 不自己 `new` Repository，而是由外面创建好、通过 `__init__` 传进去。好处是：换测试环境时，可以传一个假的 Repository，不用改 Service 代码。

### 4.2 实体层：`entities/table_info.py`

```python
@dataclass
class TableInfo:
    id: str
    name: str
    role: str
    description: str
```

**为什么要有实体层？** 因为各层之间要传"表"这个概念。用 dataclass 传，字段名有类型检查，拼错立即报错；用 dict 传，`table["nmae"]` 打错了要到运行时才炸。

**实体 vs 模型（最关键的区别）：**

| | entities/ | models/ |
|---|---|---|
| 是什么 | 业务实体 | ORM 模型 |
| 依赖 | 只依赖 `dataclass` | 依赖 SQLAlchemy |
| 给谁用 | Service、Repository、Mapper 之间传 | 只有 Repository/Mapper 碰 |
| 类比 Java | POJO / DTO | MyBatis 的 entity（带注解） |

**为什么要拆两层？** 业务对象不能绑死数据库框架。哪天换存储，实体不用改，只改 ORM 模型和 Mapper。

### 4.3 模型层：`models/table_info.py`

```python
class TableInfoMySQL(Base):
    __tablename__ = "table_info"

    id: Mapped[str] = mapped_column(String(64), primary_key=True, comment="表编号")
    name: Mapped[str | None] = mapped_column(String(128), comment="表名称")
    ...
```

**关键点：**
- `__tablename__ = "table_info"` 告诉 SQLAlchemy 这个类对应数据库哪张表。
- `Mapped[str]` 是 SQLAlchemy 2.0 的新式类型标注，`mapped_column(...)` 定义列属性。
- `str | None` 表示可空（对应 SQL 里没加 NOT NULL 的列）。
- **类名 `TableInfoMySQL` 故意不叫 `TableInfo`**，避免和实体 `TableInfo` 重名混淆。后缀 `MySQL` 强调"这是绑定 MySQL 表的模型"。

### 4.4 转换层：`mappers/table_info_mapper.py`

```python
@staticmethod
def to_model(table_info: TableInfo) -> TableInfoMySQL:
    return TableInfoMySQL(**asdict(table_info))
```

**`asdict()` 是核心魔法。** dataclass 的 `asdict()` 把实体转成 dict：

```python
asdict(TableInfo(id="fact_quotation", name="fact_quotation", role="fact", description="..."))
# → {"id": "fact_quotation", "name": "fact_quotation", "role": "fact", "description": "..."}
```

然后 `TableInfoMySQL(**dict)` 用这个 dict 作为关键字参数构造 ORM 对象。**前提是实体字段名和模型字段名完全一致**，才能 `**` 解包对上。

**为什么单独写 Mapper 而不在 Repository 里直接转？** 集中管理转换逻辑。以后字段增加/改名，只改 Mapper 一处，不用到处找。

### 4.5 仓储层：`meta_mysql_repository.py`

```python
def save_table_infos(self, table_infos: list[TableInfo]):
    self.session.add_all(
        [TableInfoMapper.to_model(table_info) for table_info in table_infos]
    )
```

**两个关键点：**

1. **方法输入是实体，不是 ORM 模型。** 上层（Service）根本不知道 ORM 的存在，它只传 `TableInfo`。转换在 Repository 内部完成——这是"上层不碰 ORM 细节"的体现。

2. **`save_table_infos` 是普通 `def`，不是 `async def`。** 因为 `session.add_all()` 不真正执行 SQL，只是把对象"暂存"进 Session 内存（标记为 pending insert）。真正发 SQL 是在 commit 时，由异步 Session 负责。**这是最容易误解的一点**——见下面第五节。

### 4.6 编排层：`services/meta_knowledge_service.py` 的 `_save_tables_to_meta_db`

```python
async def _save_tables_to_meta_db(self, meta_config) -> list[ColumnInfo]:
    table_infos, column_infos = [], []
    for table in meta_config.tables:
        table_infos.append(TableInfo(id=table.name, ...))          # ①
        column_types = await self.dw_repo.get_column_types(table.name)  # ②
        for column in table.columns:
            column_values = await self.dw_repo.get_column_values(...)   # ③
            column_infos.append(ColumnInfo(...))                        # ④
    async with self.meta_repo.session.begin():                          # ⑤
        self.meta_repo.save_table_infos(table_infos)
        self.meta_repo.save_column_infos(column_infos)
    return column_infos
```

**注意数据来源的"混合"：**

| ColumnInfo 字段 | 来源 | 说明 |
|---|---|---|
| `id` | 拼出来的 | `f"{table.name}.{column.name}"` |
| `name` | yaml | 字段名 |
| `type` | **dw 库** | `get_column_types` 查出来的真实类型 |
| `role` | yaml | 字段角色 |
| `examples` | **dw 库** | `get_column_values` 查出来的真实样例 |
| `description` | yaml | 业务含义 |
| `alias` | yaml | 同义词 |
| `table_id` | yaml | 表名 |

**为什么 type 和 examples 要从 dw 库查，而不是写死在 yaml？** 因为它们是"真实数据库的事实"，会随数据变化。yaml 是"人的业务理解"，两者性质不同，分开维护。yaml 负责"这个字段叫什么、什么意思"，dw 库负责"这个字段实际是什么类型、真实值长什么样"。

## 五、三个最容易卡住的概念（重点看）

### 5.1 `add_all()` 不会立刻写库

```python
self.session.add_all([...])   # ← 这行执行完，数据库里还没有数据！
```

SQLAlchemy 的 Session 像一个"待办清单"：
- `add_all()` = 把对象写进清单（标记为"待插入"），**不发 SQL**。
- `commit()` / `flush()` = 才真正把清单里的操作变成 INSERT 语句发出去。

所以 `save_table_infos` 是同步方法（只改内存），真正的异步提交发生在 `begin()` 退出时。

### 5.2 事务：`async with session.begin():`

```python
async with self.meta_repo.session.begin():
    self.meta_repo.save_table_infos(table_infos)      # 表信息
    self.meta_repo.save_column_infos(column_infos)    # 字段信息
# ← 退出这个块时自动 commit
```

**为什么要把"保存表信息"和"保存字段信息"放进同一笔事务？**

因为它们在逻辑上是一个整体：一张表的信息，和这张表所有字段的信息，应该"要么都写进去，要么都不写"。

假想没有事务：先写表信息成功，写字段信息时数据库挂了 → 结果库里有一张"有表但没字段"的残缺记录。有了事务，中间任何一步失败，之前的所有操作一起回滚，库回到干净状态。

**这就是"原子性"（Atomicity）——事务的 ACID 里第一个字母 A。**

### 5.3 事务边界由谁决定？（分层的精髓）

- **Repository 的方法里没有 `begin()`/`commit()`**，只有 `add_all()`。
- **Service 里才有 `async with session.begin():`**。

原因：Repository 只负责"怎么存一条数据"，它不知道"哪几条数据该在同一个事务里"。**这是 Service（编排层）才有的业务知识**。

> 类比：仓库管理员（Repository）只负责"往仓库放货"，他不知道"这批货要不要一起验收"。项目经理（Service）才知道"这 11 张表的元数据是一批的，要一起入库验收，要么全成要么全不成"。

## 六、用一份真实数据走一遍

以 `fact_order_item.amount` 这个字段为例：

```
【yaml 配置】fact_order_item 表 → amount 字段：
  role: measure
  description: "该行产品的金额，按所属合同头的币种计价。合同金额 = SUM(该字段)。"
  alias: [金额, 合同金额, 明细金额]
  sync: false

【dw 库真实数据】
  get_column_types("fact_order_item")  → {"amount": "decimal(12,2)", ...}
  get_column_values("fact_order_item", "amount", 10) → [Decimal('123.45'), ...]

【合并成 ColumnInfo 实体】
  ColumnInfo(
      id="fact_order_item.amount",
      name="amount",
      type="decimal(12,2)",        ← dw 库
      role="measure",              ← yaml
      examples=[Decimal('123.45'), ...],  ← dw 库
      description="该行产品的金额...",   ← yaml
      alias=["金额", ...],       ← yaml
      table_id="fact_order_item",
  )

【Mapper 转 ORM】
  ColumnInfoMySQL(**asdict(column_info))
  → examples 和 alias 被 JSON 列自动序列化存储

【写库】
  INSERT INTO column_info (id, name, type, role, examples, description, alias, table_id)
  VALUES ('fact_order_item.amount', 'amount', 'decimal(12,2)', 'measure', ...);
```

最后 meta 库的 `column_info` 表里就有了这么一行完整的字段元数据，供后面问数时召回使用。

## 七、容易混淆 / 踩坑的点（汇总）

1. **`entities/` vs `models/`**：实体是纯数据（dataclass），模型是 ORM（绑定 SQLAlchemy）。字段几乎一样，但职责不同，靠 Mapper 转换。

2. **`asdict()` 的适用前提**：实体字段名必须和模型字段名一致，否则 `**` 解包会对不上。

3. **`add_all()` 不写库**：只是暂存，`commit()`/`begin()` 退出时才真正 INSERT。

4. **Repository 方法是否 async**：查数据（`get_xxx`）是 `async`（要 `await session.execute`）；写数据（`save_xxx`）是同步（只 `add_all` 改内存）。

5. **SQLAlchemy 2.0 用 `all()` 不是 `fetchall()`**：SQLAlchemy 2.0 里是 `all()`，1.x 的 `fetchall()` 已经不用了。

6. **字段 `id` 用 `表名.字段名`，表 `id` 用表名**：字段 id 天然携带所属表，后续关联不用再查 table_id。

7. **`examples` 用 `list[Any]`**：因为样例值类型不固定（金额是 Decimal、状态是 str、日期是 date），只能放宽到 Any。
