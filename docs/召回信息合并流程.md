# 召回信息合并流程（merge_retrieved_info）：全流程详解

> 本文只讲一个节点：**把三路召回结果（字段 / 取值 / 指标）聚合成 SQL 生成能直接用的上下文**。
> 目的：搞懂"为什么要合并""7 步各干了什么""真实数据一步一步变成了什么样"。

---

## 一、一句话总览

> **把三路召回的"原始命中"（字段 19 个、指标 4 个、取值 1 个）加工成两份结构化上下文：`table_infos`（按表分组的字段，补齐了主外键）和 `metric_infos`（精简后的指标）。**

7 步拆开：

| 步骤 | 干什么 | 读 MySQL? |
|---|---|---|
| ① 字段按 id 去重 | 建立"字段 id → 字段对象"的工作集合 | 否 |
| ② 补齐指标依赖字段 | 指标依赖的字段没召回，就查库补上 | 是 |
| ③ 取值合并回 examples | 把召回的取值塞进字段 examples | 否（字段不存在时才读） |
| ④ 字段按表分组 | 按 table_id 归到各自表下 | 否 |
| ⑤ 补齐主外键 | 每张表强制补主外键（Join 依赖） | 是 |
| ⑥ 生成 table_infos | 组装"表 → 字段列表"结构 | 是 |
| ⑦ 生成 metric_infos | 组装精简指标 | 否 |

其中 ②③⑤ 是**补漏**，①④⑥⑦ 是**归并重组**。

---

## 二、为什么需要这个节点（先懂"为什么"）

三路召回拿到的"原始命中"有四个毛病：

1. **字段散乱**：19 个字段平铺在一个 list 里，没有"哪张表有哪些字段"的结构。
2. **指标依赖的字段可能没召回**：指标说"我要算车间工序达成率"，但生成 SQL 得知道它依赖 `fact_production_process.process_output` 和 `fact_production_process.process_plan_quantity`。这几个字段若没被字段召回命中，就没进上下文。
3. **主外键大概率漏掉**：用户问"各车间工序达成率"，不会问"车间ID是多少"，所以 `workshop_id` 这类键字段向量召回容易漏。但多表 Join 全靠它们。
4. **字段可能重复**：不同召回分支可能命中同一个字段。

merge 节点做两件事：**补漏**（把漏掉的字段/主外键从 meta 库查回来）+ **重组**（把平铺字段按表分组、精简成模型好消费的结构）。

---

## 三、输入数据（真实召回结果）

本次演示用的是之前连通性验证跑出来的真实数据，问题：

> **近三个月各车间的车间工序达成率是多少？**

三路召回的输入：

- **字段召回（19 个）**：`fact_production_process.process_output`、`fact_production_process.process_id`、`dim_workshop.workshop_name`、`dim_date.month`……（注意：**没有** `fact_production_process.process_plan_quantity`，也没有 `dim_workshop.workshop_id`）
- **指标召回（4 个）**：车间工序达成率、车间加工量、不良率、产量
- **取值召回（1 个）**：`喷塑` → 属于 `dim_workshop.workshop_name`

4 个指标的依赖字段（来自 meta_config.yaml）：

| 指标 | relevant_columns |
|---|---|
| 车间工序达成率 | `fact_production_process.process_output`、`fact_production_process.process_plan_quantity` |
| 车间加工量 | `fact_production_process.process_output` |
| 不良率 | `fact_production_process.defect_quantity`、`fact_production_process.process_output` |
| 产量 | `fact_production.output_quantity` |

---

## 四、7 步数据流演示（核心：数据一步步变成什么样）

### ① 字段按 id 去重 → `retrieved_column_infos_map`（19 项）

```python
retrieved_column_infos_map: dict[str, ColumnInfo] = {
    retrieved_column_info.id: retrieved_column_info
    for retrieved_column_info in retrieved_column_infos
}
```

**数据变成：**

```python
{
    "fact_production_process.process_output":  ColumnInfo(id="fact_production_process.process_output", ...),
    "fact_production_process.process_id":      ColumnInfo(id="fact_production_process.process_id", ...),
    "dim_workshop.workshop_name":              ColumnInfo(id="dim_workshop.workshop_name", ...),
    "fact_production.output_quantity":         ColumnInfo(id="fact_production.output_quantity", ...),
    # ... 共 19 项
}
```

> 这次其实**没删任何东西**（字段召回内部已经去重了）。① 的真正价值是搭出"工作集合"，让后面的 ②③ 能靠 `id in map` 查重、补漏。

---

### ② 补齐指标依赖字段 → map（19 → 20 项）

逐个指标检查依赖字段在不在 map 里：

| 指标 | 依赖字段 | 在 map 里？ | 动作 |
|---|---|---|---|
| 车间工序达成率 | `fact_production_process.process_output` / `fact_production_process.process_plan_quantity` | ✅ / ❌ | **查库补 process_plan_quantity** |
| 车间加工量 | `fact_production_process.process_output` | ✅ 召回了 | 跳过 |
| 不良率 | `fact_production_process.defect_quantity` / `fact_production_process.process_output` | ✅ / ✅ | 跳过 |
| 产量 | `fact_production.output_quantity` | ✅ | 跳过 |

**关键就在"车间工序达成率"这一行**：车间工序达成率公式是 `SUM(fact_production_process.process_output) / SUM(fact_production_process.process_plan_quantity)`，它同时依赖工序实际加工数和工序计划加工数**两个**字段。但用户问的是"车间工序达成率"，"工序产出/加工量"这一层语义更像 `process_output`，所以字段向量召回只召回了分子 `process_output`，漏掉了分母 `process_plan_quantity`。② 从 meta 库把它查出来补进 map：

```python
if "fact_production_process.process_plan_quantity" not in retrieved_column_infos_map:     # 不在！
    column_info = await meta_mysql_repository.get_column_info_by_id("fact_production_process.process_plan_quantity")  # 查库
    retrieved_column_infos_map["fact_production_process.process_plan_quantity"] = column_info  # 补进去
```

**数据变成**：map 多了 `fact_production_process.process_plan_quantity` 一个字段，**19 → 20 项**。

---

### ③ 取值合并回 examples → map 仍是 20 项（但 workshop_name 的 examples 可能 +1）

```python
for retrieved_value_info in retrieved_value_infos:      # 只有 1 个：喷塑
    value = "喷塑"
    column_id = "dim_workshop.workshop_name"
    if column_id not in retrieved_column_infos_map:      # 在！跳过查库
        ...
    if "喷塑" not in retrieved_column_infos_map["dim_workshop.workshop_name"].examples:
        retrieved_column_infos_map["dim_workshop.workshop_name"].examples.append("喷塑")
```

**这一步的意义，来自一个关键事实**：

- 字段元数据的 `examples` 建库时只**抽样 10 条**（`get_column_values(table, column, 10)`）。
- ES 取值索引存的是**全量 distinct 值**（`limit 100000`）。

所以取值召回可能召回到"抽样没覆盖到"的真实值。③ 的职责就是**兜底**：取值召回到什么，就保证 examples 里有它，让模型写 `WHERE workshop_name='喷塑'` 时知道"喷塑"是真实存在的取值。

**数据变成**：`dim_workshop.workshop_name` 的 examples 里要有 `"喷塑"`（若它本来不在那 10 条抽样里的话）。map 项数不变（还是 20 项）。

> 一个真实细节：车间一共只有 6 个取值（机加工 / 制管 / 焊接 / 抛光 / 喷塑 / 包装），10 条抽样早就把「喷塑」覆盖了，所以这一次 examples 其实没变——但代码仍会**先查重再补**，保证它在。③ 想表达的不变量就是："recall 到什么取值，examples 里就一定找得到它"。

---

### ④ 字段按表分组 → `table_to_columns_map`（4 张表）

```python
table_to_columns_map: dict[str, list[ColumnInfo]] = {}
for column_info in retrieved_column_infos_map.values():
    table_id = column_info.table_id
    if table_id not in table_to_columns_map:
        table_to_columns_map[table_id] = []
    table_to_columns_map[table_id].append(column_info)
```

**数据变成**（字段从"按字段维度"重组为"按表维度"）：

```python
{
    "fact_production_process": [process_id, production_id, process_output, process_seq, defect_quantity, defect_type, process_done_date_id, process_plan_quantity],  # 8 个（process_plan_quantity 是②补的）
    "fact_production":         [production_id, order_id, product_id, output_quantity, plan_done_date_id, actual_done_date_id],  # 6 个
    "dim_workshop":            [workshop_name],                     # 1 个 ← 只有名字，缺主键！
    "dim_date":                [date_id, year, quarter, month, day],  # 5 个
}
```

> 注意 `dim_workshop` 只有 `workshop_name` 一个字段——它的主键 `workshop_id` 没被召回。

---

### ⑤ 补齐主外键 → map 增加 `workshop_id`（共 22 列）

```python
for table_id in table_to_columns_map.keys():
    key_columns = await meta_mysql_repository.get_key_columns_by_table_id(table_id)  # 查这张表的主外键
    column_ids = [c.id for c in table_to_columns_map[table_id]]                      # 当前已有的字段
    for key_column in key_columns:
        if key_column.id not in column_ids:
            table_to_columns_map[table_id].append(key_column)                        # 缺的补上
```

**逐表检查结果**：

| 表 | 主外键 | 已在列表里？ | 动作 |
|---|---|---|---|
| fact_production_process | process_id(PK) + production_id/process_done_date_id(FK) | 全部✅；**workshop_id 缺** | **补 workshop_id** |
| fact_production | production_id(PK) + order_id/product_id/plan_done_date_id/actual_done_date_id(FK) | 全部✅ | 不补 |
| dim_workshop | **workshop_id(PK)** | ❌ | **补 workshop_id** |
| dim_date | date_id(PK) | ✅ | 不补 |

**数据变成**：`fact_production_process` 和 `dim_workshop` 下面各多了 `workshop_id`。全量字段 **20 → 22 列**。

> 这就是"补漏"的第二处生效：用户问"各车间工序达成率"不会提"车间ID"，但 `fact_production_process` 要和 `dim_workshop` Join 就得靠 `workshop_id`。⑤ 无条件补齐，保证后面生成 SQL 时每张表都不缺 Join 的键。

---

### ⑥ 生成 table_infos → 4 个 `TableInfoState`

```python
table_infos: list[TableInfoState] = []
for table_id, column_infos in table_to_columns_map.items():
    table_info = await meta_mysql_repository.get_table_info_by_id(table_id)  # 查表元数据
    columns = [ColumnInfoState(name=c.name, type=c.type, role=c.role,
                               examples=c.examples, description=c.description, alias=c.alias)
               for c in column_infos]          # 字段转成精简版（砍 id/table_id）
    table_infos.append(TableInfoState(name=table_info.name, role=table_info.role,
                                      description=table_info.description, columns=columns))
```

**数据变成**（以 dim_workshop 为例，看它补齐后的完整样子）：

```python
TableInfoState(
    name="dim_workshop",
    role="dim",
    description="车间维度表，散热器工艺路线上的各道工序所在车间，共 6 个……",
    columns=[
        ColumnInfoState(name="workshop_name", type="varchar", role="dimension",
                        examples=["喷塑", "焊接", ...], description="车间名称，取值 机加工 / 制管 / 焊接 / 抛光 / 喷塑 / 包装。", alias=[...]),
        ColumnInfoState(name="workshop_id",   type="bigint",  role="primary_key",
                        examples=[], description="车间ID，主键。", alias=[...]),  # ← ⑤ 补的
    ],
)
```

> **关键变化**：字段从 `ColumnInfo`（8 字段）转成了 `ColumnInfoState`（6 字段），**砍掉了 `id` 和 `table_id`**——因为字段已经挂在某张表下面，所属表不言自明，id 对模型也是冗余。

## 六、核心概念（重点看）

### 6.1 一个 map 贯穿全程

`retrieved_column_infos_map`（字段 id → 字段对象）是 ①②③ 共用的"工作集合"：
- ① 建立它
- ②③ 往里面**补**（靠 `id not in map` 查重）
- ④ 从里面**读**（`.values()` 取字段，按表分组）

它的价值是"**按 id 快速查重**"——dict 的 key 查找是 O(1)，换成 list 就得每次遍历比对。

### 6.2 去重 vs 分组，都是 dict，但 value 不同

| | ① 去重 | ④ 分组 |
|---|---|---|
| key | 字段 id | 表 id |
| value | **单个** ColumnInfo | **list**（一张表挂多个字段） |

区别在于：一个字段只对应一个对象（单值），一张表对应多个字段（要 list 兜住）。

### 6.3 完整实体 → 简化状态（面向提示词的"投影"）

召回阶段用**完整实体**（ColumnInfo 8 字段，信息全），合并后转成**简化状态**（ColumnInfoState 6 字段，砍 id/table_id）。

原理：传给 SQL 生成模型的东西，**只留它需要的字段**，砍掉系统内部标识。好处有二——省 token、降噪。

## 七、易混淆 / 踩坑点（汇总）

1. **缩进即代码块**：`if` 里查库 + 赋值，两行都必须在 `if` 内缩进。把赋值写到 `if` 外面（和 `if` 平齐），会导致"字段已存在时也执行赋值"，此时变量未定义 → `NameError`。这是本次开发真实踩过的坑。

2. **`.values()` vs `.items()`**：① 用推导式建 map，④ 用 `.values()` 只取字段对象（不关心 key），⑥ 用 `.items()` 同时要表 id 和字段列表。三者各取所需，别混。

3. **JSON 列 raw SQL 读回是字符串**：`get_key_columns_by_table_id` 用原生 SQL 查 `column_info` 表，而 `examples`/`alias` 是 JSON 列，raw SQL 读回来是 JSON 字符串、不是 list。因为主外键通常没有 examples，暂时不影响；以后若踩到，再加 ORM 类型反序列化。

4. **②③ 都要"先查重再补"**：补字段前必须 `if xxx not in map`，否则会把已召回字段重复覆盖（虽然结果是同一个对象，但白查一次库、逻辑也乱）。

## 八、下一步

merge 节点之后，先**重排**、再**过滤**：

0. `rerank_retrieved_info`：用 cross-encoder（或确定性的「RRF + 词面」兜底）给候选打分，
   把最相关的表和字段排到前面，让 `generate_sql` 的提示词里靠前的就是最该看的。
   只排序、默认不裁剪（见 [README](../README.md#召回融合与重排)）。
1. `filter_table`：从 table_infos 里筛掉不相关的表（比如这个问题里 `fact_production` 其实用不上——本次算的是车间工序达成率，不需要「产量」那张产品级事实表，靠过滤节点去掉）。
2. `filter_metric`：从 metric_infos 里筛掉不相关的指标（比如把「产量」「不良率」「车间加工量」这种噪声去掉）。

过滤完，才把"干净的表 + 指标"交给 `generate_sql` 生成 SQL。
