# 指标入库 + 向量化：全流程详解

> 本文讲最后一条链路：**把"指标"（合同金额、合同数、合同数量、产能达成率）写入 MySQL meta 库 + 灌进 Qdrant 向量库**，供后续"问数"阶段做指标语义召回。
> 目的：搞懂"指标和字段有什么本质区别""为什么指标要多一张关联表""指标向量为什么要单独一个集合"。

---

## 一、一句话总览

> **指标不是某张表的某一列，而是由字段计算出来的派生概念。把"指标本身"和"指标依赖哪些字段"两层信息存进 MySQL，再把指标的 name/描述/别名向量化灌进 Qdrant，系统才能理解"合同金额 是 fact_order_item.amount 求和算出来的"。**

---

## 二、为什么需要"指标"这一层（先懂"为什么"）

前面三条链路都在处理**字段**（列），但用户问数时，很多问题不是问字段，而是问**指标**：

| 用户问 | 答案需要 |
|---|---|
| "销售额是多少" | 指标 合同金额 = SUM(fact_order_item.amount) |
| "订单量有多少" | 指标 合同数量 = SUM(fact_order_item.quantity) |
| "产能达成率怎么样" | 指标 产能达成率 = SUM(fact_production.output_quantity) / SUM(fact_production.plan_quantity) |

**关键区别：字段是真实存在的列，指标是"算出来"的概念。**

- `fact_order_item.amount` 是字段——你打开表能看到这一列，里面有真实的金额数字。
- 合同金额 是指标——表里没有"合同金额"这一列，它是把 fact_order_item.amount 全部加起来得到的**派生值**。

如果系统只知道字段、不知道指标，那用户问"销售额是多少"时，系统最多能召回一个字段（`fact_order_item.amount`），但**不知道"销售额 = 求和"这层计算逻辑**。指标这层就是要把"怎么算"这件事显式存下来。

> 一句话：字段回答"有什么数据"，指标回答"怎么算出那个数"。

---

## 三、这次的分层：既有 models/mappers，又有独立 Qdrant 仓储

指标的存储横跨 MySQL 和 Qdrant 两类，所以分层是前几章的"合体"：

```
写 MySQL：  MetricInfo/ColumnMetric(实体) → Mapper → ORM模型 → SQL INSERT   （有 models+mappers）
写 Qdrant： MetricInfo(实体) → asdict → payload → point                     （无 models+mappers）
```

- **MySQL 部分**和表/字段一样，需要 entities + models + mappers 三层。
- **Qdrant 部分**和字段向量一样，直接 asdict 塞 payload，没有 models/mappers。

所以指标链路比字段链路**多了一个实体**（ColumnMetric）——因为指标到字段是"多对多"，要单独表达这层关系。

## 五、完整执行顺序（4 步）

```
① 确保指标向量集合存在（第一次建，之后跳过）
   └─ metric_qdrant_repository.ensure_collection()

② 从配置把每个指标拆成 "指标本身 + 一堆字段依赖边"
   └─ MetricInfo(id=指标名, ...) × N 个
   └─ ColumnMetric(column_id, metric_id) × M 条

③ 同一笔事务写进 MySQL：metric_info + column_metric
   └─ save_metric_infos + save_column_metrics

④ 把指标 name/描述/别名 向量化后写入 Qdrant
   └─ 每个指标拆成 2 + len(alias) 个 point
```

## 六、逐层代码走读（关键代码 + 为什么）

### 6.1 实体层：`metric_info.py` + `column_metric.py`

```python
@dataclass
class MetricInfo:
    id: str                 # 指标唯一标识 = 指标名，如 "合同金额"、"合同数量"
    name: str               # 指标名（和 id 相同，保持和 ColumnInfo 结构对称）
    description: str        # 业务含义 + 计算口径，如 "SUM(fact_order_item.amount)"
    relevant_columns: list[str]   # 依赖的底层字段 ["表.字段"]
    alias: list[str]        # 同义词 → 向量化召回用
```

```python
@dataclass
class ColumnMetric:
    column_id: str          # 被依赖字段，如 "fact_order_item.amount"
    metric_id: str          # 依赖它的指标，如 "合同金额"
```

**为什么 `id` 直接用指标名？** 字段 id 要拼 `表名.字段名`，是因为 `order_id` 这个列名在很多张表里都出现（合同头、合同明细、生产指令都有）；但指标名（合同金额、产量）在整个业务里是唯一的，不需要拼前缀。

**为什么指标链路多出 ColumnMetric 这个实体？** 字段到表是"一对一"（一个字段属于一张表），用 `table_id` 一个字段就表达了。但指标到字段是"多对多"：产量依赖 `fact_production.output_quantity`，产能达成率也依赖 `fact_production.output_quantity`（一个字段被多个指标共用）；而产能达成率还同时依赖 `fact_production.plan_quantity`（一个指标依赖多个字段）。所以需要单独一条"关联边"来记录。

### 6.2 ORM 层：为什么拆成两张表

**`metric_info`** 存指标本身：

```python
class MetricInfoMySQL(Base):
    __tablename__ = "metric_info"
    id: Mapped[str] = mapped_column(String(64), primary_key=True)
    name: Mapped[str | None] = mapped_column(String(128))
    description: Mapped[str | None] = mapped_column(Text)
    relevant_columns: Mapped[dict | list | None] = mapped_column(JSON)   # 依赖字段，JSON 存列表
    alias: Mapped[dict | list | None] = mapped_column(JSON)
```

**`column_metric`** 存关联关系：

```python
class ColumnMetricMySQL(Base):
    __tablename__ = "column_metric"
    column_id: Mapped[str] = mapped_column(String(64), primary_key=True)
    metric_id: Mapped[str] = mapped_column(String(64), primary_key=True)
    # 联合主键 (column_id, metric_id)：同一对关系只允许出现一次
```

**关键问题：依赖关系在 `metric_info.relevant_columns`（JSON）里已经存了，为什么还要单独建 `column_metric` 表？**

这是"冗余换查询效率"的典型做法，因为两个查询方向都要快：

| 查询方向 | 用哪张表 | 为什么 |
|---|---|---|
| "产能达成率 依赖哪些字段"（正向） | metric_info.relevant_columns | 读指标那一行就有，不用 join |
| "fact_order_item.amount 被哪些指标用"（反向） | column_metric | 按 column_id 一查就有，不用全表扫 JSON |

问数阶段"召回字段后要反查它支撑哪些指标"，反向查询会频繁发生，所以单独建表值得。

### 6.3 仓储层：MySQL + Qdrant 两处

**MySQL 仓储**新增两个方法（和 save_column_infos 一模一样的套路）：

```python
def save_metric_infos(self, metric_infos: list[MetricInfo]):
    self.session.add_all([MetricInfoMapper.to_model(m) for m in metric_infos])

def save_column_metrics(self, column_metrics: list[ColumnMetric]):
    self.session.add_all([ColumnMetricMapper.to_model(cm) for cm in column_metrics])
```

**Qdrant 仓储**（`metric_qdrant_repository.py`）几乎和字段仓储一样，只有两处不同：

1. `collection_name = "metric_info_collection"`（字段是 `column_info_collection`）
2. `search()` 还原成 `MetricInfo` 而不是 `ColumnInfo`

**为什么指标要单独一个集合？** 字段和指标是两类对象：字段回答"有哪些列"，指标回答"有哪些可算的数"。混在一个集合里，搜"数量"会同时召回字段 `quantity` 和指标 `合同数量`，问数阶段很难区分。分开存，召回各归各的。

### 6.4 编排层：两个新方法

**`_save_metrics_to_meta_db`**——把指标和依赖关系一起落库：

```python
for metric in meta_config.metrics:
    # ① 指标本身 → MetricInfo
    metric_info = MetricInfo(
        id=metric.name, name=metric.name,
        description=metric.description,
        relevant_columns=metric.relevant_columns,
        alias=metric.alias,
    )
    metric_infos.append(metric_info)

    # ② 每个依赖字段 → 一条 ColumnMetric 关联边
    for column_id in metric.relevant_columns:
        column_metrics.append(ColumnMetric(column_id=column_id, metric_id=metric.name))

# ③ 指标 + 关系放进同一笔事务：要么全成功，要么全回滚
async with self.meta_mysql_repository.session.begin():
    self.meta_mysql_repository.save_metric_infos(metric_infos)
    self.meta_mysql_repository.save_column_metrics(column_metrics)
```

**`_save_metric_info_to_qdrant`**——和 `_save_column_info_to_qdrant` 逻辑完全一样，只是对象从 ColumnInfo 换成 MetricInfo，集合换成 metric_info_collection。一个指标拆成 `name + description + 每个 alias` 共 `2 + len(alias)` 个 point。

## 七、四个核心概念

### 7.1 指标 vs 字段（本质区别）

| | 字段（ColumnInfo） | 指标（MetricInfo） |
|---|---|---|
| 是什么 | 表里真实的一列 | 由字段算出来的派生概念 |
| 例子 | fact_order_item.amount | 合同金额 = SUM(amount) |
| 有没有实体列 | 有，打开表能看到 | 没有，是计算规则 |
| 关联关系 | 字段→表：一对一（table_id） | 指标→字段：多对多（column_metric） |

### 7.2 拆两张表：metric_info + column_metric

- `metric_info` 存"指标是什么"（名称、口径、别名）。
- `column_metric` 存"指标依赖谁"（关联边）。
- 依赖关系在两处都存（JSON 冗余 + 独立表），是为了正向、反向查询都快。

### 7.3 联合主键 (column_id, metric_id)

两个字段共同作为主键，含义是"同一对 (字段, 指标) 关系只允许一条"。这样即使重复构建时漏了去重，数据库层面也不会插入重复的关联边（会撞主键报 1062 而不是默默多插一行）。

### 7.4 独立的 metric_info_collection

指标向量单独一个集合，和字段的 `column_info_collection` 分开。这样问数阶段"召回字段"和"召回指标"是两次独立的检索，结果不会混在一起。

## 八、用真实数据走一遍

以配置里的 4 个指标为例：

```
【yaml 配置】 metrics: [合同金额, 合同数, 合同数量, 产能达成率]

【拆成实体】
  MetricInfo(id=合同金额, relevant_columns=["fact_order_item.amount"], alias=[销售额,销售总额,营收,订单金额,合同总额,成交金额,接单金额])
  MetricInfo(id=合同数, relevant_columns=["fact_order.order_id"], alias=[合同笔数,订单数,订单笔数,合同个数,接单数])
  MetricInfo(id=合同数量, relevant_columns=["fact_order_item.quantity"], alias=[订单量,合同件数,订购数量,下单数量])
  MetricInfo(id=产能达成率, relevant_columns=["fact_production.output_quantity","fact_production.plan_quantity"], alias=[计划达成率,生产达成率,产能利用率])

【ColumnMetric 关联边（5 条）】
  合同金额→fact_order_item.amount；合同数→fact_order.order_id；
  合同数量→fact_order_item.quantity；
  产能达成率→fact_production.output_quantity、产能达成率→fact_production.plan_quantity

【写 MySQL】
  metric_info 4 行 + column_metric 5 行

【写 Qdrant：每个指标拆 2 + len(alias) 个 point】
  合同金额   1名+1描述+7别名 = 9
  合同数     1名+1描述+5别名 = 7
  合同数量   1名+1描述+4别名 = 6
  产能达成率 1名+1描述+3别名 = 5
  合计 = 27 个 point
```

> 注意这套别名的口径陷阱：「销售额」只挂在「合同金额」上，「订单量」（件数）只挂在「合同数量」上、「订单数」（笔数）只挂在「合同数」上。这三者语义很近，正是最容易召回错的地方。

**最终验证结果（本次真实运行）：**

| 存储 | 结果 |
|---|---|
| MySQL metric_info | 4 行 |
| MySQL column_metric | 5 行 |
| Qdrant metric_info_collection | 27 个 point（green） |

## 九、容易混淆 / 踩坑的点

1. **指标链路和字段链路共享同一个 MetaMySQLRepository**：`save_metric_infos` 和 `save_column_infos` 都在同一个 repository 里，只是方法不同。别想成"指标要新建一个 repository"——MySQL 仓储是给整个 meta 库用的，表/字段/指标都归它管。

2. **指标向量的 payload 里带着 `relevant_columns`**：Qdrant 的 point payload = `asdict(MetricInfo)`，里面包含了 `relevant_columns`。所以问数阶段召回指标后，能直接从 payload 知道"这个指标依赖哪些字段"，不用再回 MySQL 查一次。

3. **MySQL 依旧不幂等**：`metric_info` 主键是指标名、`column_metric` 主键是联合主键，重复构建会撞主键报 1062。所以重跑前要 `DELETE FROM meta.metric_info; DELETE FROM meta.column_metric;`（连同 table_info、column_info 一起清）。

4. **Qdrant 依旧累加（uuid 不幂等）**：指标 point 的 id 也是 `uuid.uuid4()`，重复跑会在 27 个基础上再加 27 个。要干净重跑就得先删集合（`curl -X DELETE localhost:6333/collections/metric_info_collection`）。

5. **`metric_info.id` 用中文（合同金额）当主键**：MySQL 的 VARCHAR + utf8mb4 支持中文主键，功能上没问题。但真实系统里更常见的是用英文稳定标识（如 `contract_amount`、`contract_count`）当主键，中文只当展示名——因为主键要参与 join、要稳定、要避免重命名。本项目从简，直接用指标名当 id。

## 十、下一步

至此，知识库构建的四条链路全部打通：

```
✅ 表 + 字段 → MySQL meta 库（结构化元数据）
✅ 字段 → Qdrant 向量库（语义召回）
✅ 字段取值 → ES（全文检索）
✅ 指标 → MySQL + Qdrant（指标入库 + 向量化）
```

**构建阶段结束，整个项目进入"问数"阶段**——这是 tmp_repo 里 `app/agent/nodes/` 那一大堆节点要做的：

1. 从用户问题里提取关键词（`extract_keywords`）
2. 召回指标（`recall_metric`）→ 召回字段（`recall_column`）→ 召回枚举值（`recall_value`）
3. 合并召回结果（`merge_retrieved_info`）
4. 生成 SQL（`generate_sql`）→ 校验（`validate_sql`）→ 执行（`run_sql`）

这四类检索（指标、字段、取值）现在都有数据了，下一步就是把"问数"阶段的召回和 SQL 生成串起来。
